Credit Card Default Prediction Using Random Forest

Can a customer's repayment history and account information from April–September 2005 tell us who will miss their payment in October 2005, and does a random forest do that better than simple alternatives?

1. The question

Using what a bank knew at the end of September 2005, can we predict which credit card customers will default on their October 2005 payment?

  • One row = one credit card client in Taiwan, with their demographics, credit limit, six months of repayment status, bill amounts and payment amounts.
  • Target = default.payment.next.month (1 = defaults in October 2005, 0 = does not).
  • When the prediction is made: after the September 2005 statement. Only April–September information is used.
  • Why it matters: the two mistakes are not equal. A missed default (false negative) is a loss the lender did not see coming; a false alarm (false positive) means a reliable customer is treated as risky. We therefore report precision, recall and F1, not accuracy alone.
Project scope. This study explores the use of Random Forest to predict credit card payment defaults using historical customer data from Taiwan, with a focus on model performance, evaluation, and key predictive factors.

2. The data

We use the Default of Credit Card Clients dataset from the UCI Machine Learning Repository (Yeh & Lien, 2009), loaded from its Kaggle copy (uciml/default-of-credit-card-clients-dataset). It is publicly available; we do not redistribute the raw file in this repository.

Key variables

  • LIMIT_BAL: credit limit. SEX, EDUCATION, MARRIAGE, AGE: demographics.
  • PAY_0, PAY_2–PAY_6: repayment status for September back to April (−1 = paid on time, 1–9 = months of delay). PAY_0 is the most recent month.
  • BILL_AMT1–6: bill statement amounts. PAY_AMT1–6: amounts paid.

What the data tells us first

Default is strongly linked to recent repayment status. Customers already one month late in September are much more likely to default in October.

Data-quality issues we found

  • Undocumented category codes. EDUCATION has codes 0, 5, 6 outside the documented 1–4 (345 customers, 1.15%); MARRIAGE has code 0 (54 customers, 0.18%). Repayment status contains codes −2 and 0 that the dataset description does not explain.
  • Class imbalance. About 78% of customers do not default, so a model that never predicts default is already about 78% accurate.
  • Duplicate feature profiles. No duplicate IDs, but 56 rows share identical features with another customer.

3. Preprocessing and why

DecisionReason
Group EDUCATION codes 0, 5, 6 with “other” (4); MARRIAGE 0 with “other” (3)Keeps every customer while avoiding tiny categories with unclear meaning. A practical assumption, not evidence the groups are equivalent.
Keep repayment-status codes unchangedPreserves the original information without guessing what undocumented codes mean.
Keep duplicate feature profilesDifferent customers can share identical attributes; IDs are unique.
Drop IDAn identifier carries no information about repayment.

No leakage. The only transformation is a fixed recode of category labels. It learns nothing from the data, so it cannot leak information from validation or test customers. All 30,000 rows and 23 features are kept.

4. Baselines and methods

We start with simple references and only then use a more complex model, so any gain from the random forest can be judged against something meaningful.

  • Majority-class baseline. Always predicts “no default”. Shows what class imbalance alone delivers.
  • Repayment rule. Predict default when PAY_0 ≥ 1 (already late in September). No training; uses one variable.
  • Decision tree. One shallow, regularised tree (depth 5, at least 20 customers per leaf, balanced class weights).
  • Random forest (main model). Many trees, each trained on a bootstrap sample and a random subset of features at each split; predictions are averaged. This reduces the instability of a single tree and can capture interactions between repayment history, bills and payments. Its assumptions are mild (no scaling, no linearity), but it is harder to interpret than a rule or a single tree.

5. How we evaluated

21,000training (70%)
4,500validation (15%)
4,500test (15%)
  • Split. Stratified random split (random_state=42), so each part has about 22.1% defaulters. Splits are disjoint (checked in code), and the exact customer IDs are saved in the repository.
  • Roles. Models are fitted on training; every comparison and tuning decision uses validation; the test set was used once, for the final chosen model only.
  • Metrics. Precision: of customers flagged, the share who really default. Recall: of real defaulters, the share we catch. F1: balance of the two. Average precision (PR-AUC) and ROC-AUC: quality of the probability ranking regardless of threshold. Accuracy is shown but interpreted against the 78% baseline.
  • Selection criterion. Mainly validation F1, also looking at recall, average precision and model complexity.

6. Tuning the random forest

We varied one setting at a time, then searched combinations. All of this used the validation set.

What each experiment showed (validation set)
SettingFinding
Maximum depth (5 to unlimited)Training F1 increased substantially with tree depth, while validation F1 showed only minor improvements, suggesting that deeper trees were increasingly overfitting the training data.
Class weighting“Balanced” raised recall (e.g. 0.354 to 0.577) and F1 (0.461 to 0.536 with leaf 20), at the cost of precision.
Features per split“sqrt”, 0.5 and all features gave similar F1 (0.512–0.538).
Combined grid (24 settings)Top configurations were close; the best three were compared with 300, 500 and 1000 trees.

Selected configuration: 300 trees, maximum depth 12, minimum 10 samples per leaf, 50% of features considered at each split, balanced class weights, bootstrap sampling, and random_state=42.

This configuration achieved a validation F1-score of 0.5454 and average precision of 0.5480. It was selected through our validation-based hyperparameter experiments, considering classification performance and model complexity.

The tree-count analysis showed that performance largely stabilized as the number of trees increased. We therefore retained the selected 300-tree configuration for final evaluation.

Takeaway. Validation performance improves substantially with the initial increase in the number of trees, while further increases produce only small changes. The 150-tree configuration achieves an F1-score of 0.5459, compared with 0.5454 for the selected 300-tree model. However, the 300-tree model achieves slightly higher average precision (0.5480 vs. 0.5451). We therefore retained the previously selected 300-tree configuration for final evaluation.

8. Error analysis

Who does the model miss?

We split the test customers by whether September's repayment code was positive (PAY_0 ≥ 1, already late).

  • With a positive delay code, the model detects 90.43% of actual defaulters. Without one, only 20.87%.
  • Of the 432 missed defaults, 383 (88.66%) are customers with no positive delay code.

The model relies heavily on recent repayment behaviour and struggles with customers who default despite showing no delay. These are exactly the less obvious risks a lender would most want to find.

9. Limitations

  • Dataset scope: The model was developed using Taiwanese credit card data from 2005. Its performance on other datasets or time periods has not been evaluated.
  • Missed defaults: The model correctly identifies 56.63% of actual defaulters, leaving 43.37% undetected.
  • Difficulty identifying less obvious defaults: Recall is only 20.87% for defaulters without a positive September repayment-delay code, compared with 90.43% for those with one.
  • Model selection: Several Random Forest configurations achieved similar validation results, so the selected hyperparameters cannot be considered universally optimal.
  • Interpretability: Feature importance indicates which variables influence the model's predictions, but does not establish causal relationships.

11. Conclusion

A tuned random forest (300 trees, depth 12) predicts October 2005 default with test F1 0.547 and ROC-AUC 0.777, better than the majority baseline (which finds no defaulters). On the validation set it also beat the repayment rule (F1 0.5454 versus 0.4975) and a single decision tree (0.5227). The improvement over the simple rule is real but moderate. Recent repayment status is the main signal, and the model's main weakness is customers who default without a prior delay. The number of trees mattered little beyond about 150, and the choice of threshold changes the balance between missed defaults and false alarms far more than small tuning differences.
